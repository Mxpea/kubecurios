# 专用服与真实客户端验收

仅在用户明确选择代测后搭建和启动。用户自己测时，把下列操作和预期写进 `kjs/test.md`，不启动任何实例。代测仍要邀请用户进服操作，说明连接地址、所需权限、该测哪些步骤；用户暂时无法参加时，区分 agent 已观察到的项目与尚待用户验证的项目。

## 版本基线与依赖

下表来自仓库 `gradle.properties`、`build.gradle` 的 Java toolchain 和已有实际联机验收的两端模组列表。每次以当前配置和目标 JAR 再核对；不要把基线当成对其他版本的测试结果。

| 组件 | Windows 本地联机基线 |
| --- | --- |
| Java | 64 位 Java 25；确认服务端和启动器实际使用的 Java，检查 `java -version`，不要只看系统默认版本 |
| Minecraft / NeoForge | `26.1.2` / `26.1.2.130` |
| KubeCurios | `1.2.0`（`kubecurios-1.2.0.jar`，或经确认的目标构建） |
| KubeJS | `26.1.2-8.0.8`（NeoForge） |
| Rhino | `2101.2.8-build.91` |
| Curios API | `15.0.0+26.1.2`（NeoForge） |
| Better Advanced Tooltips | `2601.1.0-build.11`，两端都装；此版组合在专用服也需要 |

- 模组配方涉及的模组和传递前置都要加入，按它们的端别安装；所有需要双端的模组（尤其提供注册项、网络协议和目标配方内容者）两端版本一致。不要把仅客户端模组装进专用服。缺少可用 JAR、兼容版本或用户的获取许可时，要求用户提供依赖并把对应测试标「阻塞」。
- **Max Health Fix 1.2 不默认安装**。仅在用户明确要求验证重连血量兼容且确认适用时，在隔离服务端做有／无对照，记录配置与结果。生命上限恢复不代表当前血量也恢复。

## 准备与启动

1. 建立两套独立游戏目录，如工作区内 `build/kubecurios-playtest/<project>/server` 和 `…/client`。使用新测试世界；若确需现有世界，经授权后先在停服状态完整备份并用副本。不要覆盖、清理或借用用户正在使用的配置、存档、端口或登录目录。
2. 可直接用该版本 NeoForge 专用服发行安装器和用户确认的客户端启动器（给客户端设置独立 game directory 与 Java 25），也可复用已配置的 NeoForge 开发运行配置，但必须核对游戏目录与实际加载产物。Windows 专用服安装器可用 Java 25 在隔离目录执行 `java -jar <NeoForge-installer.jar> --installServer`，按生成文件使用 `run.bat nogui`；安装前确认来源和目标目录，需接受 EULA 时由用户明确同意，不擅自替用户接受。发行 JAR 和开发 source set 二选一，勿把同一模组装两次。
3. 用同一份交付产物布置两端：同版本必要 JAR、完全相同的注册及命名效果启动脚本，客户端有对应资源；服务端放配方等服务端脚本，并把世界数据包放到实际 `level-name` 的世界目录下。启动前核对两端关键 JAR 和脚本的版本或 SHA-256。不要把仓库 `examples/attribute-smoke/automated/` 放进手测服，它会主动停服。
4. 本机联机用 `server-ip=127.0.0.1`，先查空闲 `server-port`（例如 `25573`，不是固定值）；默认不关闭在线验证，不开放公网、不开端口转发。启动专用服，等日志出现 `Done` 并确认数据包、依赖和脚本已载入，再启动独立客户端，连接 `127.0.0.1:<port>`。只有用户需要操作客户端时才打开可见窗口；由用户处理登录，不收集或记录凭据。若使用后台进程，给服务端保留可正常发送控制台命令的通道，同时记录本次进程标识，供结束时核验。
5. 让用户用该测试客户端进服。说明如何拿样品、进入 Curios 功能槽、切生存或第三人称，提供每件物品的预期、复现步骤和对照；仅对测试实例中获授权的用户授予必要测试权限。用户无法本机连接或操作时，不用其他测试冒充该验收。

## 测什么、怎么测

按此次实现挑选测试项，不适用项写明原因。检查双端日志中的脚本、注册表、资源和配方错误；`Done` 和能登录只证明启动和连接成功。

| 范围 | 建议操作与证据 |
| --- | --- |
| 注册与槽位 | `/give` 完整 ID，核对名称、图标、工具提示；实际戴上／取下，检查允许和拒绝的物品、目标实体及功能格与外观格的差别。 |
| 属性与伤害 | 记录裸装、佩戴、卸下的 `/attribute` 数值；用同一条件下的固定基础伤害对照目标实际扣血，排除护甲、吸收、抗性、无敌帧等干扰。命令探针与客户端挥击分别记录。 |
| 触发、概率、冷却 | 区分命中、受伤和环境伤害，验证执行者、成功条件和冷却内／外；优先用 0% 和 100% 验证边界，中间概率报告样本数和触发数，单次成功或失败不是概率验证。 |
| 耐久与计时 | 生存模式、先用无附魔样本。周期扣损等实际 `onTick`，命中扣损确认目标掉血；分别记扣损前后、破碎和换新。累计时长记录卸下／停用／破碎空档、同款双戴、重连及重启，不把动作栏刷新当作扣损证据。 |
| 资源与佩戴外观 | 真客户端查看背包、本体模型、提示及 `F5` 第三人称挂点；对照原版盔甲优先、卸下、外观栏、显示开关。若承诺他人能看到或非玩家人形支持，分别用第二客户端／目标实体实测；没有证据就标未测。 |
| 真实依赖配方 | 实际取得原料并在指定工作台或机器完成一次制作，确认输出 ID、数量和组件；核对标签与机器条件，不把 `/give`、配方浏览或成功加载当作制作成功。 |

已有源码工作区的 `runAttributeSmoke` 是额外回归（不是用户脚本和贴图验收）。获准运行时，按仓库 README 使用独立的 `build/attribute-smoke/run`，例如 `./gradlew.bat '-Pkubecurios_mods_dir=<本地模组目录>' build runAttributeSmoke`；本地依赖已完整缓存才加 `--offline`。记录实际命令和日志标记，不宣称它验证了客户端渲染或客户配方。

## 保存与关闭

- 约定测试结束后，先让用户退出或确认无需继续；从本次专用服控制台发 `save-all flush` 和 `stop`，等待保存并用日志与本次进程／监听端口确认退出。不能正常停止时先报告，不直接终止其他 Java 进程或删除测试世界。只关自己拥有且获准关闭的客户端；用户自行开的客户端请用户退出。
- 保留需要的脱敏证据和测试世界到约定时点；清理前确认目录确属本次隔离实例。将已关、保留、未关或保存无法确认如实写进 `kjs/test.md`。
