# 制作 KubeCurios 饰品脚本

按下面五步执行。每个门禁满足后才能进入下一步；待确认、静态核对和游戏内通过是不同状态。

## 1. 核对目标版本和 API

- 开工先读当前版本的两份 Wiki 和项目版本配置。**每遇到 API、版本或语义不确定，两份 Wiki 都必须查**：[KubeJS Wiki](https://kubejs.com/wiki) 和 [KubeCurios Wiki](https://github.com/Mxpea/kubecurios/blob/master/docs/wiki/Home.md)。进入对应子页核对；只打开首页不算查证。
- 用与目标版本匹配的本地源码、实际 JAR 或两者复核，不沿用旧会话、旧版示例或最新在线文档中的假定。网络受限时记录哪个来源、哪页不可达及替代证据；同分支同页的 raw 可作回退。仍有影响交付的疑点就暂停，向用户提出具体问题或索取目标版本、JAR、配方样本；不猜签名、ID、时机或资源格式。具体查法见[工程布局与 API 核对](references/layout-and-api.md)。

## 2. 向用户确认工程与物品

- 必须确认**项目名及用于文件名和 ID 的项目命名空间**、**物品大类**（如戒指、护符、腰带），以及每件物品的 ID、功能、槽位与目标实体。按大类组织注册内容；展示分类和 Curios 槽位不是一回事。
- 一并核对目标版本、效果的触发和数值、有无配方及其依赖。用户已明确的内容汇总确认，不逐项重问；只有缺少必需信息或有冲突时才暂停提问。

## 3. 向用户确认资产

- 请用户提供**每件物品的必需贴图**，注明文件来源与对应物品；复用原版或现有资产时，须有用户明确确认的资源 ID。贴图缺失、不可读取或对应不明时暂停，不擅自拿占位图当最终资产。
- 主动询问是否有**可选的物品本体模型、佩戴时的盔甲或饰品渲染模型／资源**，以及希望使用哪种显示方式。未提供可选资产本身不阻塞；用户要求特定自定义外观但缺少所需资产或当前 API 不支持时，先确认替代方案。

## 4. 实现、交付并邀请试玩

- 按[工程布局与 API 核对](references/layout-and-api.md)生成 `kjs/`：注册集中在 `kubejs/startup_scripts/<project>.js`；每个命名效果写 `kubejs/startup_scripts/<project>_<item-or-effect>.js`，顶层 `CurioScripts.define('<project>:<item-or-effect>', …)` 与 Builder 的 `.script('<project>:<item-or-effect>')` 使用完全相同的 ID。普通 KubeJS 启动、服务端和客户端事件各归其位；不要拿普通 tick 事件冒充 Curio 的命名回调。
- 交付 `kubejs/` 中的脚本和资产，以及按需单独放置的世界数据包。检查引用与文件、前置模组、配方输入输出、槽位和命名效果闭合。告诉用户放置位置、是否需重启，以及可实际操作的试玩步骤和预期。
- **始终请用户试玩，并明确问「需要我在本地搭建专用服和客户端协助测试吗？」** 已明确选择代测的可以直接按确认范围执行。没有明确同意，不安装或启动测试实例；同意后按[联机验证](references/playtest.md)起隔离环境，邀请用户进服操作并反馈。缺少用户操作或关键依赖时保留待测状态。

## 5. 记录结果并收尾

- 总是用[验收报告模板](references/test-report.md)输出 **`kjs/test.md`**，与 `kubejs/` 同级。交付但尚未实测时先列测试计划并标「未测」，每次复测和用户反馈后更新；没有真实证据或明确验收，不写「已通过」。
- 区分静态检查、自动回归、专用服、真实客户端及用户反馈。记录证据、失败、未测范围和复测步骤，不带私有绝对路径、凭据或未经脱敏的日志。若开了测试服，记录保存与关服结果；不得操作用户原实例。
