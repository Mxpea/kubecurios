# KubeCurios 下一阶段架构

状态：命名脚本效果已实现。基线：Minecraft 26.1.2 / NeoForge 26.1.2.130 / KubeJS 8.0.8 / Curios 15.0.0。

下一阶段的接口、运行语义和验收步骤见[脚本效果实现规格](implementation/curio-script-effects.md)。本文保留整体分层和兼容约束；若两处有冲突，以实现规格为准。

## 目标

整合包作者继续在启动脚本里用几行链式调用注册饰品、声明槽位并添加效果，不必自己订阅战斗事件、扫描 Curios 背包或管理冷却。内部则要做到：新增一种同类触发时，不必再实现一遍装备筛选、概率判定和命令执行。

保留上轮已验收的约定：

- `kubecurios:curio`、`.slot(...)`、`CuriosWhitelist.allow(...)`、`CuriosUtils` 和已有效果方法保持兼容，包括弃用别名。注册脚本的修改仍需要重启。
- `.slot(...)` 声明饰品可以进入哪里。**槽位定义、实体分配和数据包合并仍归 Curios**。不依赖 KubeJS 动态创建物品标签；不自动覆盖现有槽位或移除其他验证器。白名单不会为已有物品注入行为。
- 护甲、韧性和其他属性继续通过 Curios 原生属性组件生效。属性按装备格叠加；战斗倍率按物品 ID 去重。`.hideAttribute()` 不隐藏手写提示，也不影响结算。

## 现状与模块划分

目前 `CurioBuilder` 同时解析脚本参数、组装物品和内嵌穿脱回调；`CurioCombatEffects` 同时保存规则、筛选装备、计算伤害、处理受伤命令和生成提示。代码量本身不是问题，问题是这些职责各有不同的生命周期，而新增一个战斗触发会同时碰到它们。

```text
启动脚本 → CurioBuilder → 不可变饰品定义 → ScriptedCurioItem
                         ├── 属性 → Curios 原生组件
                         ├── 允许槽位 → CurioSlotWhitelist
                         └── 战斗规则 → 运行期结算 / 自动提示

服务端伤害事件 → 战斗适配器 → 查询活跃功能装备 → 计算倍率 / 执行触发规则及脚本
```

| 模块 | 职责与接缝 |
| --- | --- |
| `CurioBuilder` | 唯一的饰品声明入口。归一化脚本参数，在注册时冻结定义，把稳定的物品 ID、声明槽位和效果交给物品。属性 ID 校验、属性修饰符 ID 和白名单写入顺序保持兼容；不在 Builder 中写事件处理。 |
| 饰品定义与 `ScriptedCurioItem` | 定义保存校验后的声明，不包含实体状态。物品适配 Curios 的穿脱回调和工具提示；倍率结算和触发条件不写进物品类。工具提示读取同一份倍率规则，不另外维护一套数值。保持规则迭代顺序及现有提示顺序。 |
| 活跃装备查询 | 统一判定「当前功能格启用且有物品」，排除外观栏；`CuriosUtils.isEquipped(...)` 仍接受任何物品，战斗额外要求是声明了该槽位的 KubeCurios 饰品且有相应规则。**按 ID 去重只发生在战斗投影**，不改变穿脱回调或原生属性。 |
| 战斗结算 | NeoForge 监听器负责把 `LivingDamageEvent.Pre/Post` 转成战斗场景。`Pre` 合并内置与脚本伤害倍率；`Post` 根据实际伤害、参与者和装备运行触发。装备倍率与触发政策不直接依赖事件对象。 |
| 快捷命令触发规则 | 内部保留「触发种类 + 一条动作 + 执行对象 + 冷却 + 概率」；脚本回调不继承其冷却。先检查冷却，再掷骰，命中后先写冷却、再执行动作。规则自身不订阅事件，不持有某件物品或某个实体的运行时状态。 |

模块是职责划分，不要求每行对应一个包或公开 Java 接口。概率／冷却判定可用指定当前 tick 和随机样本来测试；装备查询继续以真实 Curios 库存测试。只为 `.script(id)` 增加启动期命名效果表；不加通用事件总线、效果 DSL 或战斗装备缓存。

### 所有权与兼容细节

- 脚本声明在物品创建时做防御性复制；属性、槽位和倍率的规则集合不由运行期改写。白名单仍在物品成功创建后填充，由 Curios 槽位验证器读取；槽位诊断仍在 Curios 数据就绪后运行。
- 战斗查询只在对应服务端伤害阶段按需读取装备，不把 `Pre` 的快照沿用到 `Post`。仅脚本的定期回调和临时属性需要低频装备检查，不能为了战斗每 tick 扫所有饰品。
- `Pre` 的倍率仍在护甲和抗性后、吸收生命扣减前生效。按现有顺序计算攻击方输出、受害方全局/匹配伤害类型倍率；环境伤害仍可应用受害方倍率。
- 冷却归 **佩戴者 × 物品 ID × 触发种类**，不是装备格，也不是 `ItemStack`。`HURT` 继续读写已有的 `kubecurios:resistance_cooldowns` 键和同一服务端 tick 时钟，不迁移旧存档。新触发用独立键。换槽、卸下重戴或同时戴两件都不能绕过同一规则的冷却；命令执行失败也不退冷却，维持现有顺序。旧 `resistanceOnHurt` 仍使用原有直接施加抗性的动作。
- 始终通过服务端执行命令，保留当前命令方块级别的权限和执行者的维度、位置、朝向。命令仍只从受信任的启动脚本声明，不开放给玩家、物品数据或网络输入。

## 脚本效果与命中后命令

`.script(id)` 绑定 KubeJS 启动脚本中通过 `CurioScripts.define` 注册的命名效果。脚本复用 KubeJS 实体读取和普通 JS `if`，也可用 `ctx.commandSucceeds(...)` 把真实命令的成功状态作为条件：明确失败返回 `false`，已提交但尚无结果返回 `true`。脚本可声明伤害倍率和临时属性，由框架负责结算与清理。

`.onHitCommand(...)` 是与脚本效果并行的快捷入口，与 `.onHurtCommand(...)` 共用命令执行、概率和冷却，但从攻击方装备出发。它可以独立验收，不是实现 `.script(id)` 的前置条件。

```js
// 提案语法，当前版本不支持 onHitCommand。
StartupEvents.registry('item', event => {
  event.create('duelist_ring', 'kubecurios:curio')
    .slot('ring') // ring 必须已分配，并引用 kubecurios:whitelist
    .onHitCommand('effect give @s minecraft:slowness 2 0 true', 120, 'target', 25)
})
```

- 与 `onHurtCommand` 一样接受正整数 tick 冷却，概率是 `0–100`、默认 `100`；可仅传第三个数值参数。每件物品每种触发最多一条命令，重复声明以最后一次为准。`self` 是佩戴者，也是该次伤害的归属攻击者；`target` 是被命中的生物。`onHurtCommand` 的 `attacker` 拼法保持不变。
- `onHitCommand` 在 `Post` 阶段触发：佩戴者是伤害归属的生物、不是受害者本人，且目标实际损失生命值。归属明确的投射物命中算射手的命中；无归属伤害、全格挡和只扣吸收生命都不触发。致命命中仍可触发以自己为执行者的命令；若命令选已死亡的目标，其结果遵循原版命令行为。
- 同一次伤害里沿用现有受击处理，再处理攻击者命中触发，各自读取当时的功能栏。受害者的 `HURT` 仍要求受害者存活；`HIT` 不继承这个条件。两种触发在同一饰品上可以共存且冷却互不影响。

暂不做：通用 `when/then`、可订阅任意事件、客户端键位扰乱、通用 Boss 不死规则、套装、自动生成槽位数据。

## 佩戴外观

`.armorAppearance` 和 `.itemAppearance` 保存纯数据声明。前者在客户端提取 Curios 的装备快照，只向原版 `HumanoidArmorLayer` 提交用于外观的物品栈副本；后者通过 Curios `ICurioRenderer` 提交绑定到骨骼的普通物品模型。两个实现都不向服务端加载客户端类，不修改背包栈或实体原版护甲格。脚本语法与资源约定见[饰品佩戴外观](wiki/Wearable-Appearance.md)。
